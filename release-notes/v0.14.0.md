A pod that never gets past its init containers now tells you which one is failing and why, instead of reporting the app container waiting behind it. The release also adds a command for changing a resource in place.

- **Init containers in the report:** A failing init container gets its own row, marked `(init)`, and becomes the pod's top finding, as in `CrashLoopBackOff in init container migrate of Pod loop (2 restarts)`.
- **Logs from the step that failed:** The report draws its log excerpt from the init container while that is the problem, labeled `init container migrate`.
- **Sidecars counted the way kubectl counts them:** A native sidecar now counts toward READY, so a finished Job pod reads `0/2` where kx read `0/1`.
- **Patching by index:** A patch reaches an indexed resource as `kubectl patch` would, as in `kx patch 1 --type merge -p '{"metadata":{"labels":{"tier":"web"}}}'`.

**Breaking:** If a CI gate runs `kx diag --fail-on critical`, a pod stuck in `Init:CrashLoopBackOff` now exits 2 where it exited 0, since the failing init container rates critical rather than warnings.
