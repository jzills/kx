A release that finishes `--sort`, adds `kx taint`, and gives an agent more of kx to read.

The `--sort` flag arrived in v0.10.0 for `kx get`, `kx top`, `kx scan` and the `kx diag` sweep. It now orders `kx events` as well, and orders the live table `kx get --watch` draws, where the two flags used to refuse each other. Completion knows the columns: `kx get pods --sort <TAB>` offers the ones kx last printed for that kind, read back from the listing it saved rather than from the cluster, and a comma carries the spec on, so `--sort status,-re<TAB>` completes to `status,-restarts`. Where the columns depend on how the table was taken — `-o wide`, `-L app`, `kubectl top --containers` — only a listing of that same shape is offered back, and completion stays quiet rather than suggest a column the sort would refuse.

A new command taints Nodes: `kx taint 1 dedicated=gpu:NoSchedule` sets one, and `kx taint 1 --remove dedicated` drops every taint with that key. It takes one index, as `kx drain` does and for the same reason: a `NoExecute` taint evicts every Pod that does not tolerate it, so setting one asks first unless you pass `--yes`. kubectl's `--all` and `--selector` are refused beside an index, because kubectl taint would apply them to every Node they select rather than to the one you numbered.

The MCP server gained two tools and two parameters. The `describe` tool returns kubectl's account of a resource, and `rollout_history` lists a workload's revisions, or one revision's Pod template. The `list_resources` and `top` tools and the `diagnose` sweep take a `sort`, and `diagnose` takes a `limit`. Every tool is still read-only against the cluster.

Either side of a copy can name its Pod by mark, so `kx cp @api:/etc/config.yaml ./config.yaml` works wherever `kx cp 3:/etc/config.yaml ./config.yaml` did.

The site was rebuilt around a landing page laid out like other command-line tools' sites, with a light/dark button, a tabbed install panel, and a page that lists every release.

Upgrading keeps your history: a `~/.kx/state.json` written by 0.10.2 resolves the same indexes. One command answers differently. A `kx describe <index>` whose resource has since been deleted used to hand kubectl the bare name, and kubectl described whatever resources that name was a prefix of — so you read about `web-canary` having asked about `web`, and the command exited 0. The resource is now named exactly, so a deleted one is reported as gone and the listing is printed fresh, the way every other index command already behaved. Nothing else asks anything of you.
