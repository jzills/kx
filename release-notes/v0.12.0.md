A release that lets kx reach a resource you can already name, without listing it first, and brings kx's reports into k9s.

Every command that takes an index now also takes the resource the way kubectl writes it: `kx diag deploy/api`, `kx logs pod/web-7d -f`, `kx delete svc/old -n staging`. Its namespace comes from `-n`, or the current one when there is none, and `--context` sends it to another cluster, so a name from an alert, a teammate or another tool's output needs no `kx get` and no counting rows. A kind/name can sit on the same line as an index or a mark, as in `kx yaml 3 deploy/api`, where it is looked for in the current namespace: `-n` and `--context` are still refused beside an index or a mark, which carry their own. A kind/name that names nothing is reported as `Deployment/typo was not found in namespace 'default'.` and your saved listing is not run again, since no listing produced it.

The commands that change the cluster take kind/name too, among them `kx delete`, `kx scale`, `kx rollout`, `kx drain` and `kx set image`, and every kubectl call they make goes to the cluster `--context` chose. A prompt before something is removed names that cluster: `Delete Deployment/api in default on context 'prod'?`. Beside a kind/name, `--context` also reaches `kx diag`, `kx tree`, `kx scan`, `kx events`, `kx labels` and `kx mark`, and an `--html` report's command line names the namespace and context it ran against. A mark can pin a resource by name, as in `kx mark api deploy/api`, so `@api` works later without a listing.

A k9s plugin pack binds five keys that run `kx diag`, `kx tree`, `kx scan`, `kx events` and `kx mark` on the row under k9s's cursor, in that row's namespace and k9s's context. It is one file, installed with `curl`; the guide at https://jzills.github.io/kx/docs/guides/use-kx-from-k9s/ shows where it goes. Shift-K is the bridge back: it marks the row, so `kx logs @api -f` reaches the same resource from a plain terminal once k9s is closed.

Upgrading asks nothing of you. Every argument kx accepted before is read as it was, and a `~/.kx/state.json` written by 0.11.1 resolves the same indexes. A kind/name used to be refused as "not a valid int", and `--context` on `kx diag` and its neighbors as not a flag; both are now accepted, so a script that relied on those refusals will see them succeed.
